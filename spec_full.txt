# Quotes Connect — Antigravity Remediation & Polish Specification

> **Purpose:** This document is the execution specification for bringing the current Quotes Connect codebase from its audited state to a coherent, secure, production-grade implementation.
>
> **Audience:** Antigravity / autonomous coding agent working directly in the repository.
>
> **Primary instruction:** Do not treat this as a checklist of isolated bugs. Treat it as a product, architecture, security, and UX reconciliation task. Preserve the project's core philosophy while fixing contradictions, incomplete implementations, security boundary failures, and the parts of the UI that currently feel like an engineering dashboard instead of a finished product.

---

# 0. Mission

Quotes Connect is a privacy-first, graph-oriented knowledge and conversation system.

The product is built around:

- passages / quotes as first-class objects
- explicit relationships between objects
- people / authors as first-class identities
- tags and semantic grouping without a recommendation algorithm
- a Billboard-style public discovery surface
- graph traversal and contextual exploration
- sovereign user identity
- encrypted local keystores
- encrypted peer communication
- an encrypted relay used for transport coordination rather than plaintext key exchange
- explicit user-controlled relationships
- multiplatform clients
- Compose Multiplatform
- Ktor
- SQLDelight
- Kotlin / Gradle

The implementation must preserve these principles.

The objective is **not** to redesign Quotes Connect into a conventional social network, recommendation engine, feed reader, or generic notes application.

The objective is:

> **Make the existing idea trustworthy, coherent, secure, visually mature, and internally consistent.**

# 2. Absolute Engineering Rules

These rules override convenience.

## 2.1 Never fake security

Never use:

- placeholder public keys
- placeholder private keys
- fake signatures
- fake encryption
- pseudo-random IDs presented as cryptographic keys
- `PUB-WEB-*`
- `PRIV-WEB-*`
- Base64 encoding presented as encryption
- hashes presented as encryption
- client-supplied identity as authentication
- unauthenticated ephemeral server keys presented as MITM protection

If a secure primitive is unavailable on a platform:

1. implement a real platform-specific primitive,
2. use a well-maintained cryptographic implementation,
3. or fail closed.

Never silently downgrade.

---

## 2.2 Never silently weaken the security model

A secure operation must not become plaintext merely because:

- the secure transport failed,
- the platform lacks an implementation,
- a key is unavailable,
- a token is missing,
- the browser cannot access a native API,
- a server endpoint is easier to call without authentication.

Explicit failure is preferable to insecure success.

---

## 2.3 Identity is not authorization

Never trust:

```text
authorId
userId
senderId
ownerId
principalId
```

because the client supplied it.

The server must derive authenticated identity from the authenticated session / credential.

If an endpoint modifies private state:

```text
authenticated principal
        ↓
authorized resource
        ↓
operation
```

must be enforced server-side.

---

## 2.4 Documentation must describe reality

Do not update documentation merely to claim a feature is implemented.

Every statement such as:

- implemented
- supported
- encrypted
- authenticated
- multiplatform
- persistent
- secure

must correspond to working code.

If a feature is incomplete, mark it as incomplete.

Requirements:

- actual key generation

# 6. Fix Web Keystore Unlock

The current web keystore unlock path is not sufficient if it only accepts a passphrase and then treats encrypted bytes as plaintext or performs no real decryption.

Implement a real encrypted keystore lifecycle.

Recommended model:

```text
passphrase
    ↓
KDF
    ↓
key-encryption-key
    ↓
decrypt encrypted keystore
    ↓
validate authenticated encryption
    ↓
load identity
```

Use a modern password-based key derivation function appropriate for the platform.

Use authenticated encryption.

Store:

- KDF parameters
- salt
- nonce / IV
- ciphertext
- authentication tag where applicable
- format version

Never store:

- plaintext private keys
- plaintext passphrases
- recoverable passphrases
- private keys in logs

Wrong passphrase must produce a clean failure.

Corrupt ciphertext must produce a clean failure.

# 8. Peer Key Exchange Architecture

The intended architecture is:

```text
Peer A
   │
   │ encrypted session establishment
   ▼
Server relay
   │
   │ encrypted relay channel
   ▼
Peer B
```

The server is a transport facilitator.

It must not become the place where plaintext key material is exchanged.

## Required properties

Both peers must be active when the exchange is explicitly initiated.

The exchange should be session-oriented.

The server should relay encrypted protocol messages.

The server must not receive:

```text
plaintext private keys
plaintext session keys
plaintext shared secrets
```

The system must not require:

```text
peer A → direct IP → peer B
```

The intended model is an encrypted relay channel rather than direct IP-to-IP communication.

# 9. Relay Protocol

Define an explicit protocol version.

For example:

```text
RelaySession
    sessionId
    protocolVersion
    initiator
    responder
    createdAt
    expiresAt
    state
```

Messages should have explicit types.

For example:

```text
HELLO
KEY_OFFER
KEY_RESPONSE
AUTH_PROOF
READY
PAYLOAD
CLOSE
ERROR
```

Every message should be:

- versioned
- authenticated where appropriate
- encrypted where appropriate
- bounded in size
- associated with a session
- rejected after expiry
- rejected if sent by the wrong participant

Do not make the relay an opaque bag of arbitrary JSON.

# 10. Relay Authorization

A relay session must bind to exactly the intended participants.

Example conceptual rule:

```text
session A ↔ B

A may send only as A
B may send only as B
everyone else is rejected
```

Do not trust:

```text
senderId
recipientId
participantId
```

without validating them against the authenticated session.

# 11. HTTP MITM Protection

The existing documentation claims protection that is stronger than the current implementation provides.

Fix the trust model.

An ephemeral server public key is not sufficient protection if the client has no authentic trust anchor.

Define one of these explicitly:

### Option A: Certificate / public-key pinning

The client knows an expected server identity.

### Option B: Trusted bootstrap key

A long-lived trusted public key signs ephemeral session keys.

### Option C: OS / browser trust infrastructure

Use authenticated TLS correctly and explain what it protects.

Do not claim:

> MITM protected

unless there is an actual trust chain.

Document the exact threat model.

# 13. Server Authorization Audit

Perform a complete endpoint-by-endpoint authorization review.

Create a table internally:

| Endpoint | Read/Write | Authentication | Resource Owner | Authorization |
|---|---|---|---|---|

For every private endpoint ask:

1. Can an unauthenticated caller reach it?
2. Can the caller choose the identity being modified?
3. Can the caller choose another user's ID?
4. Can the caller modify another user's keystore?
5. Can the caller publish as another user?
6. Can the caller delete another user's data?
7. Can the caller open a relay session for another identity?
8. Can the caller impersonate a chat participant?

Fix every instance of:

```kotlin
if (principal != null && principal != suppliedId)
```

when the intended behavior is:

```text
authentication required
AND
authenticated identity == resource owner
```
